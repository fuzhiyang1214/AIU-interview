# career/ · 我的足球生涯

> 自建球员 → 排兵布阵 → 记录比赛 → 生涯沉淀。把「我自己的球队」这套数据管起来，
> 让创意作品不只分析别人，也能记录自己。

## 一句话定位

前面的 `vision/` 和 `players/` 都是**看别人**（分析画面、查真实球员）。
`career/` 补上另一半：**写自己**——我自己建的球员、我自己摆的阵、我自己踢的比赛。
四块内容是一条线，不是四个孤立工具：

```
自建球员（能力值） → 战术板排兵布阵 → 录入比赛结果 → 生涯统计与成长曲线
   squad.py            formations.py      matches.py        stats.py
```

## 数据模型（SQLite，5 张表）

存储用 Python 标准库 `sqlite3`，**零新增依赖**。库文件默认在 `football/data/career.db`。

| 表 | 存什么 | 关键点 |
|---|---|---|
| `my_player` | 自建球员：六维能力 + 位置 + 年龄/号码/惯用脚 | **总评不落库**，每次读取现算 |
| `player_snap` | 能力快照（每次改动能力值留一条） | 生涯页的成长曲线就画它 |
| `formation` | 战术板存档：站位 + 球位（归一化坐标 JSON） | 存**坐标**不存画面，换屏幕尺寸也对得上 |
| `matches` | 比赛：日期 / 赛事 / 双方 / 比分 / 关联阵容 | — |
| `appearance` | 出场明细：谁上、踢哪、出场分钟、进球、助攻、评分 | `side` 分「我方 / 对手」 |

### 为什么总评不落库

总评 = `位置权重 × 六维能力`。如果存下来，以后**一改评分口径，历史数据就是脏的**。
现在每次读的时候现算，库里只有原始能力值 —— 调权重，全库总评自动跟着变，不会出现
「同一个球员两种算法结果」的鬼影。

### 为什么删球员不删他的战绩

删除球员时只把他的出场记录 `player_id` **解绑**（置空、保留名字），他变成一条
「历史球员」继续出现在生涯表里。理由是：**「把人移出球队」和「把历史抹掉」是两回事** ——
否则删一个球员，他打过的比赛、进过的球会直接从战绩里消失，等于篡改历史。

## 评分规则（`ratings.py`）

同一个能力组合，打不同位置价值完全不同：**速度 90 / 防守 40 的球员，在边锋位是快马，
在中卫位是漏勺**。所以总评按位置加权（每行权重和为 1），而不是简单平均。

| 位置 | 速度 | 射门 | 传球 | 盘带 | 防守 | 身体 |
|---|---|---|---|---|---|---|
| GK | 0.08 | 0.02 | 0.10 | 0.05 | 0.45 | 0.30 |
| CB | 0.10 | 0.02 | 0.10 | 0.06 | 0.47 | 0.25 |
| CM | 0.12 | 0.10 | 0.32 | 0.20 | 0.16 | 0.10 |
| CAM | 0.14 | 0.20 | 0.30 | 0.26 | 0.04 | 0.06 |
| LW / RW | 0.32 | 0.20 | 0.14 | 0.28 | 0.02 | 0.04 |
| ST | 0.24 | 0.38 | 0.08 | 0.20 | 0.02 | 0.08 |

**门将说明**：本项目只有六维，没有单独的扑救/手型维度。门将沿用同一套六维，
把 `defending` 解释为「门线技术 / 站位」、`physical` 解释为「弹跳与对抗」——
这样前端不必为门将单开一组滑块。

### 两个踩过的坑

1. **门将不参与跨位置比较**。门将和中卫的能力画像高度重合（都靠 defending + physical），
   放开比会把中卫算成门将，很外行。所以「建议位置」的规则是：当前是门将就只认门将，
   不是门将就只在场上位置里找。
2. **舍入规则必须两端一致**。Python 的 `round()` 是银行家舍入（`round(84.5) = 84`），
   前端 JS 的 `Math.round` 是四舍五入（`84.5 → 85`）。口径不一会出现「拖滑块显示 84、
   一保存变 85」的鬼影。统一成 `floor(x + 0.5)`。

> 🔴 **求解总评的公式只有一份，就在 `ratings.py`。**
> 最早为了「拖动滑块实时看总评」，前端 `index.html` 里也抄了一份 `calcOverall()` ——
> 结果同一套规则两份实现，还得靠「两边都用四舍五入」人工对齐才不会打架。
> 这正是规范第 4 条说的「前端只负责 UI」的反面教材：**需要刻意同步才一致的代码，就是耦合**。
> 现在前端拖滑块时 POST `/api/career/rate` 问后端（90 ms 防抖），
> 删掉了那份本地公式 —— 权重改了，界面自动跟着变，不可能对不上。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/career/meta` | 评分规则的描述（位置列表 + 六维名），前端据此建表单 |
| POST | `/api/career/rate` | 六维 + 位置 → 总评 + 建议位置（**前端实时总评走它**） |
| GET / POST | `/api/career/squad` | 我的球员：列表 / 新建 |
| GET / PUT / DELETE | `/api/career/squad/<pid>` | 我的球员：详情 / 修改 / 删除 |
| GET | `/api/career/squad/<pid>/snapshots` | 能力快照（成长曲线） |
| GET / POST | `/api/career/formations` | 阵容存档：列表 / 新建 |
| GET / PUT / DELETE | `/api/career/formations/<fid>` | 阵容存档：详情 / 修改 / 删除 |
| GET / POST | `/api/career/matches` | 比赛记录：列表 / 新建（含出场明细） |
| GET / PUT / DELETE | `/api/career/matches/<mid>` | 比赛记录：详情 / 修改 / 删除 |
| GET | `/api/career/summary` | 生涯总览：战绩 + 球员榜 + 时间线 |

## 目录内文件

| 文件 | 职责 |
|---|---|
| `db.py` | 建表、连接、schema。`conn()` 是上下文管理器，每次操作新建连接换线程安全 |
| `ratings.py` | 位置权重表 + 总评计算 + 建议位置（纯函数，无 IO） |
| `squad.py` | 自建球员 CRUD + 快照 |
| `formations.py` | 阵容存档 CRUD |
| `matches.py` | 比赛与出场明细 CRUD |
| `stats.py` | 生涯统计聚合（只读） |
| `__init__.py` | 统一出口，对外只暴露动作，不暴露表结构 |

**依赖方向**：`app.py → career/*`，`career` 内部不反向依赖 `vision` / `brain`。
`stats.py` 是唯一读多表的文件。

## 覆盖数据库位置

默认写到 `football/data/career.db`。要换位置（比如跑测试用临时库）：

```
FOOTBALL_CAREER_DB=D:\tmp\career.db
```

> ⚠️ `career.db` 是**个人数据**，不应提交到仓库 —— `.gitignore` 里排除它。
> 程序首次运行会自动建库建表，不依赖仓库里有这个文件。

## 已知局限

| 局限 | 说明 |
|---|---|
| 单机单用户 | 没有账号体系，SQLite 本地文件，不做并发写优化 |
| 统计口径 | 场次/胜平负只算 `matches`；球员数据只统 `side='me'` 的出场行 |
| 无赛季概念 | 比赛按日期排序，不按赛季分组（数据量大了再加） |
| 评分是「相对口径」 | 权重表是为**业余球员**调的（没有 EA FC 那么细的细分维度），别拿它当职业标准 |
