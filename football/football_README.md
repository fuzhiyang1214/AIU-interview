# football/ · AI 战术分析师

> 任务五 · 创意作品。拍一张球场画面，它分出两队、判断谁在进攻谁在防守、指出哪条通道有空当，再用本地大模型推演**球接下来可能怎么走**。

## 一句话定位

业余球队最缺的不是训练，是**临场看不懂对面**。这个作品把「看」和「想」两件事交给 AI：
**截图 → 判攻防态势 → 找空当通道 → 推演球的发展**；画面认不出人时，**换手动战术板自己摆**。
除此之外还有一半面向自己：**自建球员 → 排兵布阵 → 记录比赛 → 生涯沉淀**。

> 设计取舍：**不做球队识别，也不硬套 4-3-3 这类阵型名**。理由有两条 ——
> ① 静态单帧本就不足以断定精确阵型，编一个像模像样的阵型反而误导；
> ② 呼应题目第 2 页那句「**做减法，而不是不断增加噪声**」。
> 只保留最可解释、最有用的两个结论：**谁压上、球可能往哪走**。

## 它回答题目的哪几句

| 题目原文 | 本作品怎么对上 |
|---|---|
| 任务四：「尽情结合你的**专业方向和兴趣方向**」 | 兴趣 = 足球，专业 = AI |
| 任务五：「在上述基础上完成**创意作品**」 | 同时用上任务一（LLM）＋任务二（YOLO）＋任务四（Harness） |
| 「AI 会把事情变繁琐，你需要**做减法**」 | 不新增框架、不新增依赖、不改 `core`；功能也刻意收敛到两条 |

## 功能怎么落地

| 功能 | 实现 | 位置 |
|---|---|---|
| ① 判断**谁在进攻、谁在防守** | **谁控球谁进攻**（球在球员脚下，距离 < 1.2 倍身高） | `vision/pitch.py` |
| ② 指出**空当通道** | 沿「通道轴」分三段，看**防守方**哪一段人最少 | `vision/pitch.py` |
| ③ 推演**球可能的发展** + ④ **战术问答** | 结构化「局面简报」→ 本地大模型 | `brain/` |
| ⑤ **手动战术板**（自己排兵布阵） | 拖动摆位 → 构造等效坐标 → **复用同一个判定内核** | `tactics/` |
| ⑥ **我的足球生涯**（自建球员 / 比赛 / 统计） | SQLite + 位置加权总评 + 成长曲线 | `career/` |

> **判定为什么优先看球权**：v2 用「越线人数」推谁在压上，在真实直播帧上**判反过**
> —— 球明明在浅蓝队 11 号脚下，却报红队在进攻。两个原因：① 侧高位机位下球场纵深其实是**横轴**
> （那帧球门在画面左侧），「越线」统计成了画面上下这条无关的轴；② 「谁占哪半场」是拿质心反推的，
> 两队挤在同一侧时整体翻过来。改成「谁控球谁进攻」后这条判据与机位、朝向都无关；
> 球没检出就**相持**，不给反的结论。详见 [`vision/vision_README.md`](vision/vision_README.md)。

## 架构（沿用题目要求的分层与前后端解耦）

```
输入（两条路，同一个判定内核）
   截图 ──────────────┐
   战术板（手动摆位）──┴──→ vision/pitch.py  判攻防 + 空当（纯计算）
                                 │
├─ vision/   帧输入(上传图/摄像头) → 裁到球场+清看台 → 检测 → 球衣分两队 → 判攻防 + 空当（纯计算）
├─ tactics/  手动站位 → 等效坐标 → 复用 vision/pitch（纯计算，不改判定逻辑）
├─ brain/    局面简报 → 本地大模型 → 态势 / 球的发展 / 问答     （纯推理）
├─ players/  球员库：本地 EA FC 数据集（评分）+ TheSportsDB（头像 / 简介）
├─ career/   我的生涯：自建球员 / 阵容存档 / 比赛记录 / 统计（SQLite，纯本地）
│
├─ app.py    Flask 后端：只做组装，暴露 /api/analyze /tactics/* /advise /ask
│                        + /api/player/* + /api/career/*
├─ static/   前端：只负责 UI 组织与请求（零推理逻辑）
└─ test/     自测脚本 + 结果 + 截图（接口 47/47、分队 10/10、判定 15/15）
```

| 目录 | 职责 | 不负责 |
|---|---|---|
| `vision/` | 看得懂画面 | 不碰网络、不碰 LLM |
| `tactics/` | 接得下手动站位 | **不重写判定**（只构造坐标喂给 `vision/pitch`） |
| `brain/` | 说得出人话 | 不碰图像、不碰 HTTP |
| `players/` | 查得到球员（搜索 / 榜单 / 能力卡） | 不碰图像、不碰 LLM；**评分离线，头像在线** |
| `career/` | 存得住自己的数据（球员 / 阵容 / 比赛 / 统计） | 不碰图像、不碰 LLM、不碰网络 |
| `app.py` | 组装 + 暴露接口 | 不写算法、不写提示词、不写 SQL，**也不碰图像（不 import cv2 / numpy）** |
| `static/index.html` | UI 组织与显示（六个视图） | **零推理**（连球员总评都问后端，前端不存评分公式） |

> 视觉层是**纯计算**：想换后端（比如换成云端模型）只改 `brain/`，`vision/` 一个字不动。
>
> **两条输入路径共用一个判定内核**是刻意的设计：战术板不复制 `pitch.py` 的逻辑，
> 只把坐标构造出来。所以截图分析和手动摆阵**结论口径天然一致**，
> 也不会出现「同一局面两套说法」。

> 📦 `data/` 里除 `players_ea_fc.csv`（球员库数据集）和 `career.db`（我的生涯数据）外，
> 早先的球队库 / 在线赛程源 / 颜色匹配器**已不参与主流程**，作为历史实现保留备用。

## 怎么跑起来

**桌面版（推荐，观感是一个独立应用）**

> 想只验证链路不开窗口：`D:\envs\yolo\Scripts\python.exe desktop.py --check`

## 为什么不用重新训练

足球场上的人是 COCO 的 `person` 类（id 0）——
这一类本来就在 80 类预训练权重里。**换任务 = 换权重，不是换代码**，所以视觉这一环零标注、零训练。

## 球员库（搜球员 / 看能力 / 出榜单）

除了「战术分析」，前端还有一个「球员库」页签 —— 库里躺着 **18494 名球员**（EA FC 26 数据集），
可以按名字搜、按任意能力维度出榜单、点开看能力卡（总评 / 六维 / 身价 / 简介）。

| 数据 | 来源 | 特点 |
|---|---|---|
| 评分与属性 | [`mzafram2001/ea-fc`](https://github.com/mzafram2001/ea-fc) | 一次性下载入库（5.7 MB），**离线可查**，秒级响应 |
| 头像与简介 | TheSportsDB（免 key） | 按需联网，**失败自动降级**成纯离线卡 |

设计上刻意把两件事分开：**评分离线、头像在线** —— 断网时球员库照样能用，只是没有头像；
联网时也只在搜索 / 详情时发 1 ~ 2 个请求（榜单默认纯离线，否则一屏 20 人要等 30 秒）。

> 详细说明见 [`players/players_README.md`](players/players_README.md)。

## 手动战术板（排兵布阵）

截图分析有个天生的短板：**COCO 认不出高位/俯视画面里的球员**——而那才是战术分析最需要的视角。
战术板直接绕过检测：**自己把球员拖到场上、标成我方/对手、放上球**，系统接着算。

关键点是**不复制判定逻辑**：`vision/pitch.py` 只认坐标，不关心坐标是 YOLO 给的还是鼠标拖的。
战术板只负责把「点位」构造成等效矩形，攻防判定 / 三区人数 / 空当通道全部原样复用。

| 能力 | 说明 |
|---|---|
| 拖动摆位 | 点选后可改位置、号码、换边、删除 |
| 一键铺开 | 5 套常用站位当**起点**（不是阵型约束，摆完随便拖） |
| 载入自建球员 | 把「我的球队」的球员摆上场，带名字与号码 |
| 存档 / 读取 | 存进 `career/`，可反复调用 |
| 空当高亮 | 分析后把最空的通道标在半透明区域上 |

> 详细说明见 [`tactics/tactics_README.md`](tactics/tactics_README.md)。

## 我的足球生涯（自建球员 / 比赛 / 统计）

前面几块都是**看别人**，这一块补上**写自己**：自建球员 → 排兵布阵 → 录入比赛 → 生涯沉淀。

| 模块 | 能做什么 |
|---|---|
| 我的球队 | 建球员、拖六维滑块（**拖动即时看总评**）、自动提示「更适合踢哪」 |
| 比赛记录 | 录入日期/赛事/双方/比分 + 出场明细（分钟、进球、助攻、评分） |
| 生涯 | 战绩卡、球员生涯榜、射手榜、**能力成长曲线**、最近比赛时间线 |

两个值得一提的设计：

- **总评不落库**：总评 = 位置权重 × 六维能力，每次读取现算。这样以后调权重口径，
  全库总评自动跟着变，不会出现「库里存着旧算法结果」的脏数据。
- **删球员不删战绩**：删除时只把他的出场记录解绑（保留名字），他作为「历史球员」
  继续出现在生涯表里。「把人移出球队」和「把历史抹掉」是两回事。

存储用 Python 标准库 `sqlite3`，**零新增依赖**，库文件在 `data/career.db`（首次运行自动创建）。

> 详细说明见 [`career/career_README.md`](career/career_README.md)。

## 已知局限（如实标注）

| 局限 | 说明 |
|---|---|
| **视角** | 只吃**高位/侧高位**画面；纯俯视（鸟瞰）下球员太小且非直立，COCO 大概率认不出。画面的纵深轴按**转播机位**约定取横轴，竖向取景的画面请走战术板 |
| **球的检测** | 整屏截图里球只有 ~12px，整图推理（1280~2560）**检不出来** ⇒ 改为「裁到球场 + 在球员脚边开小窗」找球（实测置信度 0.29 → **0.78**）。仍被完全遮挡/运动模糊时会漏，**漏了就不判攻守（相持）**，不硬猜 |
| **草地背景干扰分队** | 取样框里混进草色会把球员判给错的一队（实测草地像素占取样区 **7%~69%**）⇒ 已改为「胸区取样 + 剔除草地色 + 色相主峰」 |
| **看台观众混进来** | COCO 把观众也认成 `person`（实测 10 人变 17 人）⇒ 按「框底边附近草地占比」剔掉，并兜底「剔太多说明掩膜不可靠，就全部保留」 |
| **球衣颜色接近** | 两队颜色相近（红 vs 橙）会分不开队（两个色心几乎重合时**不硬分**，退回亮度通道） |
| **门将异色** | 门将球衣与两队都不同（**深色门将 ↔ 草地暗部色相撞车**）⇒ 判为「异色」并**踢出攻防统计**，但标不出他属于哪一队。深色球衣的门将取样区若落到草地，色相离本队色心仅 ~23°，靠 `gk_tol=22°` 才挡得住；分辨率变化时偶尔会被归进某队（人数多算 1 人，不影响球权判定） |
| **黑衣裁判** | 取样干净的**黑/白球衣**走亮度通道能识别；但取样框边缘混进场地像素时，仍可能被算进某一队 |
| **越线启发式** | 只在**战术板**（没摆球时）保留：那块画布的朝向是约定死的（y=0 = 对方球门），且用户摆位时两队各占半场。真实画面**不走**这条 —— 正是踩过的坑 |
| **人数** | 检出人数是近似：重叠的两人可能出两个重叠框（**不去重** —— 实测有一红一蓝两人 IoU 0.69，合并会误删真人） |
| **单帧** | 只有一张静态画面，看不到跑动趋势，推演是**或然性**判断，不是预测 |
| **战术板需手动** | 摆位靠拖，不自动识别画面里的人（这是绕过检测短板的手段，不是缺陷） |
| **生涯数据单机** | 没有账号体系，SQLite 本地文件；统计口径按 `side='me'` 的出场行计 |

以上局限在 `vision/` 的注释与 [`vision/vision_README.md`](vision/vision_README.md) 里都标了原因，属**已知取舍**而非 bug。
战术板的意义正是**把第一条的短板绕过去**：认不出的画面，手摆就一定能分析。
