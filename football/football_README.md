# football/ · AI 战术分析师

> 任务五 · 创意作品。拍一张球场画面，它分出两队、判断谁在进攻谁在防守、指出哪条通道有空当，再用本地大模型推演**球接下来可能怎么走**。

## 一句话定位

业余球队最缺的不是训练，是**临场看不懂对面**。这个作品把「看」和「想」两件事交给 AI：
**截图 → 判攻防态势 → 找空当通道 → 推演球的发展**。

> 设计取舍：**不做球队识别，也不硬套 4-3-3 这类阵型名**。理由有两条 ——
> ① 静态单帧本就不足以断定精确阵型，编一个像模像样的阵型反而误导；
> ② 呼应题目第 2 页那句「**做减法，而不是不断增加噪声**」。
> 只保留最可解释、最有用的两个结论：**谁压上、球可能往哪走**。

| 题目原文 | 本作品怎么对上 |

## 三个功能怎么落地

| 功能 | 实现 | 位置 |
|---|---|---|
| ① 判断**谁在进攻、谁在防守** | 球的位置 → 或「越线人数」启发式 | `vision/pitch.py` |
| ② 指出**空当通道** | 画面横向分左/中/右三通道，看防守方哪条人最少 | `vision/pitch.py` |
| ③ 推演**球可能的发展** + ④ **战术问答** | 结构化「画面简报」→ 本地大模型 | `brain/` |

## 架构（沿用题目要求的分层与前后端解耦）

```
截图
 │
 ├─ vision/   检测 person/sports ball → 球衣分两队 → 判攻防 + 空当（纯计算）
 ├─ brain/    画面简报 → 本地大模型 → 态势 / 球的发展 / 问答     （纯推理）
 │
 ├─ app.py    Flask 后端：只做组装，暴露 /api/analyze /advise /ask
 └─ static/   前端：只负责上传、显示、发送（零推理逻辑）
```

| 文件 | 职责 | 不负责 |
|---|---|---|
| `vision/` | 看得懂画面 | 不碰网络、不碰 LLM |
| `brain/` | 说得出人话 | 不碰图像、不碰 HTTP |
| `app.py` | 组装 + 暴露接口 | 不写算法、不写提示词 |
| `static/index.html` | UI 组织与显示 | **零推理** |

> 视觉层是**纯计算**：想换后端（比如换成云端模型）只改 `brain/`，`vision/` 一个字不动。

> 📦 `data/`（球队库 / 在线赛程源 / 颜色匹配器）**当前不参与主流程**，作为历史实现保留备用。
> 需要"认球队 / 查赛程"时再接回来即可，`vision/`、`brain/` 都不用动。

## 为什么不用重新训练

足球场上的人是 COCO 的 `person` 类（id 0）——
这一类本来就在 80 类预训练权重里。**换任务 = 换权重，不是换代码**，所以视觉这一环零标注、零训练。

## 已知局限（如实标注）

| 局限 | 说明 |
|---|---|
| **视角** | 只吃**高位/侧高位**画面；纯俯视（鸟瞰）下球员太小且非直立，COCO 大概率认不出 |
| **球的检测** | COCO 的 `sports ball` 在本场景**很不可靠**（大特写会被误判为 kite，小目标又常漏检）⇒ **攻防判定优先走「越线人数」这条不依赖球的路径** |
| **球衣颜色接近** | 两队颜色相近（红 vs 橙）会分不开队 |
| **越线启发式** | 「越线人数」假设画面为纵向构图、中线在画面中部；横构图或极端视角下会失准 |
| **单帧** | 只有一张静态画面，看不到跑动趋势，推演是**或然性**判断，不是预测 |

以上都在 `vision/` 的注释里标了原因，属**已知取舍**而非 bug。
