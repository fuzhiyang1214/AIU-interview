# vision/ · 视觉分析层

把「画面」变成「谁在哪、谁在进攻、哪条通道空」。**纯计算**，不碰网络与 LLM。

```
帧输入（上传图 / 摄像头）
      frames.py
            ↓
   ① 裁到球场 + 清看台 + 按需放大      locate.py
            ↓
   ② 检测球员与球                     detector.py
            ↓
   ③ 球衣分两队                       team_split.py
            ↓
   ④ 攻防态势 + 空当判读               pitch.py
            ↓
   __init__.py 串成 analyze_image() → (结构化结果, 带标注的图)
```

| 文件 | 职责 |
|---|---|
| `frames.py` | 帧的**来源**：上传的 data URL 解码、本机摄像头采集（两个函数都返回 BGR） |
| `locate.py` | **预处理**：草坪色最大连通块 → 球场区域；按长边换算推理尺寸；剔看台观众；在球员脚边开窗找球 |
| `detector.py` | 加载 COCO `yolov8n.pt`，只保留 `person` 与 `sports ball` |
| `team_split.py` | 取球员**胸区**主色 → 直方图主峰定两队 → 判不出队的标 `gk` / `unknown` |
| `pitch.py` | 由**球权**+两队位置推断攻防态势、空当通道与静态发展线索 |
| `__init__.py` | 串起四步，输出结构化字典 + 带标注的图（`analyze_image`） |

> `frames.py` 独立出来的原因：解码与采集都要碰 OpenCV，属视觉层的活。
> 放在这里，主程序 `app.py` 就**不必 import cv2 / numpy** —— 这才叫「主程序只做组装」。

## 为什么要先裁到球场（locate）——这一层是后来补的，理由都是实测

截图往往是**整块桌面**（3072×1920），球在画面里只有 ~12px。同一帧实测：

| 做法 | 球的检出 |
|---|---|
| 整图 imgsz=1280 / 1920 / 2560 | **检不出来**，只有门将手套的误检 |
| 裁到球场后 imgsz=3200 | 置信度 0.29（还被手套压过） |
| **在球员脚边开小窗、窗内 imgsz=640** | **置信度 0.78，且窗里没有它的对手** |

球检不出来，攻守就只能靠站位猜 —— 而站位猜正是「攻守判反」的根源之一。
所以：先裁到球场，再在每名球员脚边开窗找球。

顺带解决两件事：
- **看台观众**会被 COCO 认成 `person`，混进分队与人数统计（实测 10 人变 17 人），
  判据是「框底边附近的草地占比」（真球员的脚一定在草地上）。
- 裁剪后球员变大，**漏检明显减少**；同时把界面上的浅绿卡片、图标排除在球场之外。

> **一个坑**：`cv2.connectedComponentsWithStats` 返回的 `stats` 是 **np.int32**，
> 把它直接塞进响应会让 Flask 报 `TypeError: Object of type int32 is not JSON serializable`。
> 坑在于**只有「真裁到球场」这条分支才踩得到** —— 拿普通照片测（走「返回整幅」分支）测不出来。
> 所以 `pitch_roi` 的返回值统一 `int()` 过一遍，并在 `test_judge.py` 里立了 K6 钉住它。

> **另一个坑（字段被同名覆盖）**：`analyze_image` 把判定层展开成 `**geo` 来拼返回体，
> 而 `geo` 里也有一个 `"unassigned"` —— 它是**裸 int**（人数），会把前面精心搭好的
> `{"count", "gk", "unknown"}` 结构化版本整个盖掉。前端读 `a.unassigned.count` 于是拿到
> `undefined`，「未计入（门将 / 裁判）」那一行**在界面上永远不出现**
> （症状：显示「球员总数 9 = 5 + 3 + 1」，却看不到多出来的那 1 人）。
> 修法是把 `**geo` 提到前面展开、结构化字段放后面覆盖上去；
> 接口自测里加了一条 CHECK 钉住「`unassigned` 是结构化字段 + `players == on_pitch + count`」。
> 🚩 **教训**：返回体里出现**同名字段**时，字典字面量的**书写顺序就是覆盖顺序** —— 谁在后谁赢。

## 攻防判定（pitch）—— v3 改过一次，因为判反了

v2 用「画面纵轴 = 球场纵深、画面中线 = 球场中线」+「两队质心各自占半场」推谁在压上。
两个硬伤：

1. **机位不一定是纵向的**。侧高位机位下球场纵深其实是**横轴**（实测那帧球门在画面左侧），
   于是「越线人数」统计的是画面上下 —— 一条与攻防无关的轴。
2. **「谁占哪半场」是拿质心反推的**（循环论证）。一旦两队挤在同一侧，归属就整体翻过来。
   实测：球明明在浅蓝队 11 号脚下，却被判成红队在进攻。

v3 改成三条：

| 优先级 | 判据 | 说明 |
|---|---|---|
| ① | **谁控球，谁进攻** | 球到最近球员的距离 < **1.2 倍身高** 才算「在他脚下」。控球是定义进攻方最直接的一手，与机位、朝向无关 |
| ② | 球检出但离谁都远 | **相持**，理由写明「球权不明，不判攻守」—— 宁可说不知道，不给反的结论 |
| ③ | 图像路径没检出球 | **相持**，只给站位事实。例外见下 |

**坐标口径**（两条路径的画法约定不同，各用各的，都不靠猜）：

| 路径 | 纵深轴 | 通道轴 | 方向词 |
|---|---|---|---|
| 真实画面（转播机位） | 画面**横轴**（球门在两翼） | 画面纵轴 | 纵深 `左/中/右`、通道 `下/中/上` |
| 战术板（画布约定 y=0 为对方球门） | 画布**纵轴** | 画布横轴 | 纵深 `上/中/下`、通道 `左/中/右` |

> 方向词是**按实际朝向生成的**，读者可以直接把数字对回画面 —— 不会再出现
> 「球明明在左边，却说往右推进」这种账。
>
> 曾经想用「门将地标」（门将站在本方球门）来估纵深轴，**放弃了**：门将的归属本身就要靠颜色猜
> （实测同一帧两种分辨率下，一个判对了、一个被归队），拿它当基准会把整条轴带偏。
> 朝向这件事宁可约定死。

**战术板的例外**：画布朝向是约定死的，且用户摆位时两队各占半场，
所以**没摆球**时仍走 v2 的**越线人数**（`basis = "position"`）；
摆了球但球权不明（球在空档里）时不再拿站位补结论，直接给相持。
真实画面**永远不走**这条兜底 —— 这正是踩过的坑。

**空当**：把球场按通道轴分三段，看**防守方**哪条通道人最少（`gap_channel`）。
输出里带方向词，和上面那张表的「通道轴」对齐。

**不做阵型命名**：只给三段人数这种可解释的分布，不硬套 `4-3-3`。

## 分队（team_split）—— 这块踩过坑，写细一点

在真实直播帧（草地背景）上，最初的做法会把**蓝队球员判成红队**、**黑衣裁判判进红队**，
最终把 8 个人读成 7:3。逐层定位后重写，改成四件事：

| 环节 | 做法 | 为什么 |
|---|---|---|
| 取样 | **胸部**：纵向 15%~40%、横向 35%~65% | 原来的 20%~55% / 25%~75% 太大，实测取样区内草地像素占 **7%~69%** |
| 背景 | 从画面四周 14px 边框估**草地色**，剔除色相接近且亮度也接近的像素 | 这是「蓝队球员被判成红队」的主因 |
| 取色 | 36 桶色相直方图取**主峰**（并记录纯度） | 中位数会被草地拉走 —— 实测某蓝队球员的取样中位数是草色，主峰才是蓝 |
| 归队 | 两队色心同样取**主峰**；`min(色距) > 22°` → `gk`；纯度 < 45% / 取样不足 / 黑白但与两队亮度都对不上 → `unknown` | k-means 均值色心实测 27/84，真值约 16/98 |
| 兜底 | 两个色心几乎重合（两队同色）→ 不硬分，交给亮度通道 | 宁可不分，也不制造"假的"分队 |

> **阈值为什么是 22°**：真实直播帧里**深色球衣的门将**（黑 / 深灰）取样区常落在球衣之外的**草地暗部**，
> 采出的色相离本队色心只有约 **23°** —— 原来的 28° 会把他吸进某一队。
> 收紧到 22° 后门将正确剔除，而正常球员离本队色心通常 < 13°，不受影响（分队自测 10/10 通过）。

**黑白球衣走亮度通道**：低饱和（S≤60）像素基本就是黑/白球衣（草地是有彩的，落在 neutral 之外），
取其中位亮度；只有当某队平均亮度与它相差 ≤ 60 时才归队。
旧实现在"有彩像素不足"时把色调硬写成 `0`，正好与红队（H≈16）撞车。

**未计入的球员不参与攻防统计**（`team = -1`）—— 异色门将本来就不在攻防结构里，
混进来只会把人数与质心带偏。他们仍然画在图上：灰框，标签 `GK` / `—`。

## 对外接口

```python
from vision import analyze_image, to_base64_jpeg
analysis, annotated = analyze_image(frame, conf=0.35, imgsz=0, device="cuda:0")
# imgsz=0（默认）= 自动：裁到球场后按长边 2.4 倍换算，夹在 1280~3200
```

`analysis` 主要字段（坐标口径 = 裁出来的球场区域，位置见 `crop`）：

| 字段 | 含义 |
|---|---|
| `counts` | `players` 检出总人数、`on_pitch` 计入攻防的人数、`team0`/`team1` 两队人数 |
| `unassigned` | 未计入攻防统计的人数（`count` / `gk` / `unknown`） |
| `players[].role` | 每人角色：`outfield` / `gk` / `unknown` |
| `crop` | `box` 球场区域在原图里的位置、`source_size` 原图尺寸、`cropped` 是否裁过、`imgsz` 实际推理尺寸 |
| `axis` | 纵深/通道轴向量 + `labels`（方向词）+ `note`（口径说明） |
| `state` / `attacking_team` / `sides` / `basis` | 攻防态势；`basis` = `ball`（控球判定）/ `position`（站位粗判）/ `none` |
| `direction` / `reason` | 推进方向（只有战术板给得出，画面单帧为 `None`）与判定依据（一句话） |
| `dist` | 两队的**纵深三段**人数（顺序 = `axis.labels.depth`） |
| `gap_channel` / `defender_channels` | 防守方最空的通道及各通道人数（顺序 = `axis.labels.channel`） |
| `ball` | 是否检出、坐标、置信度、所在纵深段与通道、**球权（owner / owner_gap）** |
| `cues` | 给上层 LLM 的事实碎片 |

## 局限（都是实测出来的，别当没看见）

- **视角**：高位/侧高位可用；纯俯视会漏检。真实画面的纵深轴按「转播机位」约定取横轴，
  所以**竖向取景的画面**（俯视战术图那种）请走战术板 —— 那块画布的朝向是约定死的。
- **球**：靠「脚边开窗」找，主路径很稳（实测 0.78），但球被完全遮挡 / 快速运动中模糊时仍会漏；
  漏了就不判攻守（相持），不硬猜。
- **门将**：深色球衣的门将 ↔ 草地暗部色相撞车，颜色法判断不了他属于哪一队。
  目前的处理是把他**踢出攻防统计**（这是对的 —— 他本就不参与攻防结构），但标不出归属；
  分辨率变化时偶尔会被归进某队，此时人数会多算 1 人（不影响球权判定）。
- **黑衣裁判**：亮度通道能处理「取样干净的黑/白球衣」，但取样框边缘一旦混进场地像素，
  他的采样色就会偏到某队一侧，仍可能被算进该队（实测一帧里裁判 H23 vs 红队 H16）。
  颜色法到此为止 —— 再往下得靠人体关键点或运动轨迹。
- **人数是检测的近似**：重叠的两名球员可能被检成两个重叠框（不去重 —— 实测有一红一蓝
  两人 IoU 0.69，合并会误删真人）。
- 两队球衣颜色接近时仍分不开（两个色心几乎重合，会退回亮度通道）。
