# tactics/ · 手动战术板

> 自己摆阵，让系统接着算。**不检测，也能分析。**

## 为什么需要它

`vision/` 那条路有个天生的短板：**COCO 权重认不出高位/俯视画面里的球员**——
而高位画面恰恰是战术分析最需要的素材（那才是能看清全队站位和空当的视角）。
纯俯视下球员又小又非直立，调检测参数是治标：**在这类图上它必然失效。**

战术板的思路是**绕过检测**：让用户（或演示时的面试官）亲手把球员拖到场上，
标成我方 / 对手，放上球，然后直接送进判定内核。于是：

| 纯截图流程 | 加战术板之后 |
|---|---|
| 上传高位图 → 检出 0 个人 → 报「未识别到球员」 | 想分析什么局面就摆什么局面，**必然出结果** |
| 面试官只能看 | 面试官可以**亲手摆一个阵型**看系统怎么判 |

而且对「分析静态局面」这个产品定位来说，**手动摆位才是正常交互** ——
真实战术分析工具（各种 tactics board）都是手摆的，没人靠自动识别。

## 核心设计：复用同一个判定内核

```
坐标来源①  截图 → vision/detector.py → 球员框
坐标来源②  战术板 → tactics/board.py → 等效球员框
                        ↓
              vision/pitch.py  analyze(players, teams, ball, size)
                        ↓
        攻防判定 / 三区人数 / 空当通道 / 判定依据
```

`vision/pitch.py` 只认「球员坐标 + 球坐标」，**它不关心坐标是 YOLO 给的还是鼠标拖出来的**。
所以战术板只要构造出等效的坐标矩形，整条判定链原样复用 —— 两条输入路径汇入同一个内核，
**结论口径天然一致**，不会出现「截图说相持、摆阵说进攻」这种自相矛盾。

## 坐标系（pitch.py 按路径约定，不靠推断）

```
逻辑画布 1050 × 680（10px ≈ 1 米，接近真实球场 105×68 的比例）

  x：0 = 左路  →  1 = 右路
  y：0 = 对方球门（进攻方向）  →  1 = 我方球门
                      ↓
  pitch.py 区分两条路径的方式很朴素：带 role 字段 = 真实画面，不带 = 战术板
  （board.py 构造的球员框没有 role）
                      ↓
  真实画面：纵深 = 画面横轴（转播镜头沿球场长边取景，球门在左右两翼）
  战术板  ：纵深 = 画布纵轴（DEFAULT_DEPTH = (0,1)，朝向约定死）
```

**为什么敢约定死**：门将归属本身要靠颜色猜（实测同一帧两种分辨率下，一个判对、
一个被归队），拿它当地标估轴会把整条轴带偏（实测轴指向了与球门相反的一侧）。
朝向这件事宁可约定死，也不要用半可靠的推断。

**越线兜底的适用范围**（v3 收窄了）：
- 战术板**没摆球**时 → 走「越线人数」（按纵深轴投影，基准 = 投影跨度的中点）
- 战术板**摆了球**时 → 走控球判定；球权不明（球在空档里、离谁都远）就报**相持**，
  不再拿站位补一个结论 —— 站位的结论更弱，会盖掉「球权不明」这个更准的判断

存进数据库（`formation.slots`）时用的是 **0~1 归一化坐标**，所以换任何屏幕尺寸、
任何画布大小，读回来都摆在同一个相对位置上。

## 起点模板 ≠ 阵型约束

`positions.py` 提供 5 套常用站位（4-4-2 / 4-3-3 / 4-2-3-1 / 3-5-2 / 5-3-2），
但**它们只是画布初值**：

- 从零手摆 11 个点太累，给个起点而已
- 摆完随便拖，**系统分析的是你实际摆出来的样子，不是模板的名字**
- 与项目一贯的取舍一致：不硬套阵型名去解释局面

镜像对手阵型时坐标做 `(1-x, 1-y)` 翻转，对手的球员自动落到对侧半场。

## 措辞适配（只翻译说法，不改结论）

`pitch.py` 的文案原本是按「图像检测」写的（「画面里只识别出一方球员」）。
战术板在 `_adapt_wording()` 里做一次措辞翻译：

| 检测口径 | 摆放口径 |
|---|---|
| 画面里只识别出一方球员 | 战术板上只摆出一方球员 |
| 球未被检出（太小或被遮挡） | 未摆放球，以上结论由球员站位推断。 |
| T0 / T1 | 我方 / 对手 |
| 战术板空着 | 战术板上还没有球员，先摆好人再分析。 |

**判定结论一个字不改**，只换说法 —— 这样两条路径的用词都贴合各自场景。
队名另有出口：`labels` 参数（`my_label` / `opp_label`）会被 `brain.prompts.brief()`
和前端横幅（`board.summarize`）优先采用，比 T0/T1 更进一步。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/tactics/meta` | 位置列表（15 个）+ 起点模板 + 画布尺寸 |
| POST | `/api/tactics/analyze` | 站位 → 与截图分析**同构**的结论 + 一句话横幅 |

请求体：

```json
{
  "slots": [{"team": 0, "x": 0.5, "y": 0.94, "pos": "GK", "no": 1}],
  "ball":  {"x": 0.5, "y": 0.3},
  "my_label": "计算机学院",
  "opp_label": "外语学院"
}
```

**关键设计**：战术板的分析结果会写进与截图分析**同一个 `STATE`**（连同队名 `labels`）。
于是 `/api/advise` 和 `/api/ask` 一行都不用改，就同时支持「看图说话」和「摆阵推演」两条路。
`brain.prompts.brief()` 也相应支持了 `labels` 参数 —— 图像场景仍输出 T0/T1（两队本来就无名），
战术板传真实队名。

## 目录内文件

| 文件 | 职责 |
|---|---|
| `board.py` | 坐标 → 等效球员框 → 调用 `vision/pitch.analyze` → 组装同构结果 |
| `positions.py` | 位置代码与中文名、5 套起点站位模板、镜像逻辑 |
| `__init__.py` | 对外出口 |

## 前端交互

- **拖动**圆点移动球员；点一下**选中**后可改位置、改号码、换边、删除
- **一键铺开**：选模板 + 选队伍 → 只替换该队（不碰另一队）
- **+ 我方 / + 对手 / + 放球** 手动增员
- **载入自建球员**：把「我的球队」里的球员直接摆上场（带名字与号码）
- **存为阵容 / 读取阵容**：存档进 `career/`，可反复调用、可删除
- 分析后**高亮空当通道**（球场左侧/中路/右侧三分之一区域半透明标出）

## 已知局限

| 局限 | 说明 |
|---|---|
| 手动输入 | 摆位靠拖，不自动识别画面里的人（这正是它的目的，不是缺陷） |
| 坐标是二维的 | 没有「球的高度」「球员朝向」，跟截图分析一样是静态二维判断 |
| 与图像分析共用进程 | `tactics` 会 import `vision`，所以必须用装了 torch 的 venv 跑（首次加载略慢） |
| 未标注球员身份 | 战术板上的点可以带名字（从自建球员载入时），但不做「谁是谁」的识别 |
